# 공개 문제지·커뮤니티 정렬 규칙

## 범위

- 문제 찾기 공개 문제지: `인기순`, `급상승`, `최신순`을 제공합니다.
- 커뮤니티 글: 같은 정렬 메뉴를 제공하되, 문제지 점수와 섞지 않고 글 좋아요만으로 정렬합니다.
- 댓글 수·댓글 작성·댓글 좋아요는 문제지와 커뮤니티 글의 인기 점수에 포함하지 않습니다. 댓글 자체의 정렬 기능은 별도입니다.
- 삭제, 공유 중지, 비공개 처리된 문제지는 공개 문제 찾기 목록에서 기존과 같이 제외됩니다.

## 문제지 활동과 가중치

| 활동 | 점수 | 기록 기준 |
| --- | ---: | --- |
| 조회 | 0.1 | 공개 카드가 화면의 50% 이상 보임. 로그인한 다른 이용자만 기록 |
| 풀이 시작 | 1 | 문제 찾기 카드에서 풀이 진입을 선택. 로그인한 다른 이용자만 기록 |
| 풀이 완료 | 3 | 서버가 공유 문제의 제출 답안을 채점하고 참여 기록을 확인한 뒤 기록 |
| 북마크 | 2 | 계정이 해당 문제지를 처음 실제로 북마크할 때 1회 기록. 해제·재등록으로 다시 가산하지 않음 |

`quiz_public_activity_weights` 테이블에서 가중치를 관리합니다. 기존 누적 조회/풀이 숫자는 이벤트 시각이 없어 7일 기록으로 변환하지 않습니다.

### 중복 제한 및 권한

- 조회와 풀이 시작은 같은 계정·문제지·활동 종류별 롤링 24시간에 한 번만 기록합니다. 서버 advisory lock으로 동시 요청도 직렬화합니다.
- 완료 이벤트는 검증된 공유 제출 ID와 점수 기록을 확인한 뒤 계정 ID 또는 지속형 익명 참여자 ID로 기록하고, 같은 제출 ID 재호출과 같은 문제지·참여자별 롤링 24시간 중복을 막습니다. 클라이언트가 점수·횟수를 보낼 수 없습니다.
- 북마크는 계정·문제지별로 한 번만 이벤트 테이블에 들어갑니다. 기존에 이미 북마크된 항목과 과거 수치는 소급 집계하지 않습니다.
- 로그인하지 않은 사람의 조회·풀이 시작은 재설정이 쉬운 브라우저 ID를 신뢰 신호로 사용하지 않고, IP 지문이나 유료 분석 서비스를 추가하지 않으므로 집계하지 않습니다. 비로그인 공유 풀이 완료는 서버 채점 후 기존 브라우저 참여자 ID로 집계합니다. 이 ID는 브라우저 저장소를 지우거나 다른 기기를 쓰면 달라질 수 있습니다. 동일 제출 ID 재요청은 별도로 중복 차단합니다.
- 이벤트·중복 방지 키·캐시 테이블은 RLS가 켜져 있고 클라이언트의 직접 읽기·쓰기를 막습니다. 8일이 지난 조회/시작/완료 이벤트는 지우지만, 다시 북마크하거나 같은 제출을 재전송해 점수를 만들지 못하도록 최초 북마크 이벤트와 제출 중복 키는 보관합니다.

## 정렬 공식

### 인기순

최근 `168시간` 내 이벤트 점수 합계 내림차순. 동점이면 최근 7일의 고유 활동자 수, 공개 시각 순으로 정렬합니다. 창은 매주 초기화하지 않고 요청 시각 기준으로 이동합니다.

### 급상승

`최근 72시간 점수 - 그 직전 72시간 점수` 내림차순. 동점이면 최근 72시간 점수, 고유 참여자 수, 공개 시각 순입니다. 소수의 반복 이벤트를 제한하기 위해 최근 72시간 활동이 3건 이상이고 고유 참여자가 2명 이상인 문제지를 먼저 보여줍니다. 아직 조건에 도달하지 않은 문제지는 뒤에 최근 활동·공개 시각 순으로 이어집니다.

### 최신순

문제지 등록/공개 시각(`published_at`) 내림차순. 활동량은 정렬에 관여하지 않습니다.

## 커뮤니티 글 정렬

- 인기순은 최근 7일 이내 현재 유효한 좋아요 수를 사용합니다.
- 급상승은 최근 72시간 좋아요 수에서 직전 72시간 좋아요 수를 뺍니다. 최근 좋아요 3개 이상, 고유 좋아요 사용자 2명 이상인 글을 먼저 놓고 최근 좋아요 수·참여자 수로 동점을 풉니다.
- 최신순은 작성 시각 기준입니다.
- 커뮤니티 댓글 수는 어떤 정렬 기준의 점수나 보조 기준에도 쓰지 않습니다. 좋아요 취소된 반응은 `community_post_likes`에 남지 않아 점수에서도 제외됩니다.

## 집계 및 비용

`quiz_public_ranking_cache`와 `community_post_ranking_cache`를 인기순·급상승 목록 RPC에서 최대 1시간 간격으로 갱신합니다. 최신순 요청은 집계를 실행하지 않습니다. Supabase Cron이나 별도 유료 서버가 필요하지 않습니다. 오래된 캐시를 처음 요청한 목록 호출이 집계를 갱신하고, 동시 요청은 DB advisory lock으로 한 번만 처리합니다. 최근 7일 밖 이벤트는 집계에서 제외하고 8일이 지난 조회/시작/완료 이벤트는 갱신 시 정리합니다. 최초 북마크 이력과 제출 중복 키는 반복 점수 방지를 위해 보관합니다. 공개 목록 필터·검색·페이지네이션은 기존 서버 RPC를 유지합니다.

## 적용 및 검증

1. `database/034_rolling_public_quiz_rankings.sql` 전체를 Supabase SQL Editor의 새 쿼리에서 실행합니다.
2. 문제 찾기 정렬 메뉴에서 `인기순 → 급상승 → 최신순` 순으로 결과가 바뀌는지 확인합니다.
3. 커뮤니티 전체 및 카테고리 필터에서 같은 정렬 메뉴를 확인합니다. 댓글 수가 큰 글이 좋아요 수와 최근성보다 먼저 올라오지 않아야 합니다.
4. 조회 새로고침, 반복 풀이 시작, 북마크 해제 후 재등록으로 이벤트가 중복 가산되지 않는지 확인합니다.
5. 기존 공개/일부 공개/비공개, 삭제, 차단, 검색, 카테고리 및 페이지네이션 동작을 확인합니다.

로컬에서는 앱 빌드와 기존 자동화 테스트를 실행할 수 있습니다. 실제 DB 동작 확인은 마이그레이션을 운영 Supabase에 적용한 뒤 위 시나리오로 확인해야 합니다.
